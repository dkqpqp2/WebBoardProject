정보공유 게시판 프로젝트 - 학습 정리노트
(PPT/면접 대비용, 질문받았던 것들 위주로 정리)

[1] Controller 관련 어노테이션
----------------------------------------

■ @Controller vs @RestController
- @Controller: 메서드가 리턴하는 문자열을 "뷰 이름"으로 해석해서 Thymeleaf가 HTML을 렌더링함
- @RestController = @Controller + @ResponseBody
  → 리턴값을 뷰 이름으로 해석하지 않고, 그 값 자체를 응답 본문(JSON 등)으로 그대로 내보냄
- 예: @RestController에서 return "list"; 라고 하면
  → list.html을 찾는 게 아니라 "list"라는 글자 자체가 응답으로 나감

■ @ResponseBody
- 메서드 하나에만 붙이면, 그 메서드만 예외적으로 JSON 응답 모드가 됨 (@Controller 클래스 안에서도 가능)
- 기술적으로는 가능하지만, 우리 프로젝트에서는 안 씀 → 이미 BoardController(REST 전용)가 따로 있어서
  섞으면 "JSON은 어디서 담당하는 거지?"가 헷갈려짐 (책임 분리 원칙 위배)

■ 왜 BoardController(REST)랑 BoardViewController(화면)를 분리했는가 (면접 대비)
- 같은 게시글 기능이라도 "소비하는 대상"이 다를 수 있음 (지금은 브라우저, 나중엔 모바일 앱/React 등)
- REST API는 그대로 재사용하고, 화면 렌더링 책임(BoardViewController)만 따로 있어서
  나중에 프론트를 분리해도 API는 안 건드려도 됨
- 실제로 두 Controller가 같은 BoardService, BoardMapper를 재사용하고 있음
  → 비즈니스 로직/DB 접근은 하나, 그 위에 응답 형태(JSON vs HTML)만 다른 Controller 두 개가 얹힌 구조

■ @RequestMapping / @GetMapping / @PostMapping / @PutMapping / @DeleteMapping
- @GetMapping 등은 사실 @RequestMapping(method=...)의 축약형
- 클래스 레벨엔 보통 공통 경로만 지정하는 @RequestMapping을 쓰고,
  메서드 레벨엔 HTTP 메서드까지 명확한 @GetMapping/@PostMapping 등을 씀
- 왜 @RequestMapping만 쓰면 안 되는가: method를 명시 안 하면 GET/POST/PUT/DELETE 요청을 다 받아버림
  → 의도한 HTTP 메서드만 받도록 제한하는 게 안전함

■ @PathVariable vs @RequestParam
- @PathVariable: URL 경로의 {값} 부분을 파라미터로 받음 (예: /board/detail/3 → 3)
- @RequestParam: 쿼리스트링(?key=value)을 파라미터로 받음 (예: ?category=GAME&page=2)
  - required = false: 값이 없어도 에러 안 나고 null 처리
  - defaultValue = "1": 값이 없으면 자동으로 이 값 사용 (required=false 효과도 포함)

■ @ModelAttribute — 두 가지 다른 의미 (헷갈리기 쉬움!)
① 메서드 위에 붙었을 때 (GlobalControllerAdvice):
   "이 메서드의 리턴값을 Model에 자동으로 넣어라" → 방향: 서버 → 화면
② 파라미터 앞에 붙었을 때 (BoardViewController의 write(), edit() 등):
   "HTML 폼에서 넘어온 값들을 이 객체에 자동으로 채워라" → 방향: 화면(Form) → 서버
   (폼 필드 name="boardTitle"과 VO 필드 boardTitle이 이름 같아야 자동 매핑됨)


[2] 전역 처리 - GlobalControllerAdvice
----------------------------------------

■ 이름을 왜 이렇게 지었나
- "Advice"는 AOP(관점지향프로그래밍) 용어로 "원래 로직에 끼어들어서 실행되는 부가 로직"
- @ControllerAdvice 쓰는 클래스는 관례상 이름 뒤에 ControllerAdvice를 붙임
- 앞의 Global은 "특정 컨트롤러 하나가 아니라 전체 컨트롤러에 적용된다"는 의미로 붙인 것

■ @ControllerAdvice가 하는 일
- "이 클래스 안의 로직을 프로젝트의 모든 @Controller에 자동으로 끼워넣어라"
- 어떤 컨트롤러 메서드가 실행되기 직전에, 이 클래스 안의 로직이 먼저 자동 실행됨
- 우리 프로젝트에서는 @ModelAttribute("loginUser")로 세션에서 로그인 사용자를 꺼내서
  모든 화면의 Model에 자동으로 넣어줌 → 매 컨트롤러마다 반복 코드 안 써도 됨


[3] Service / 의존성 주입(DI)
----------------------------------------

■ @Service
- "이 클래스는 비즈니스 로직을 담당하는 Spring 컴포넌트다" → Spring이 관리하는 객체(Bean)로 등록

■ @RequiredArgsConstructor (Lombok)
- final 필드를 파라미터로 받는 생성자를 자동 생성
- Spring이 그 생성자를 보고 필요한 객체(Mapper 등)를 자동으로 주입(DI)해줌
- 직접 new로 안 만들고 Spring 컨테이너가 대신 만들어서 넣어줌


[4] VO / Lombok
----------------------------------------

■ @Getter / @Setter
- getter/setter 메서드를 컴파일 시점에 자동 생성 (직접 손으로 안 써도 됨)

■ VO가 꼭 테이블 하나랑 1:1일 필요는 없음
- 예: BoardVO에 userName 필드 추가 (board 테이블엔 없고 user 테이블 거를 JOIN으로 끌어온 값)


[5] 앱 설정 관련
----------------------------------------

■ @SpringBootApplication
- 앱의 시작점. 자동설정 + 컴포넌트 스캔을 다 포함하는 종합 어노테이션

■ @MapperScan("com.example.board.mapper")
- 이 패키지 안의 Mapper 인터페이스들을 MyBatis가 찾아서 구현체를 자동 생성하도록 지정

■ @Bean
- 메서드가 리턴하는 객체를 Spring 컨테이너에 등록
- 예: BoardApplication의 passwordEncoder() → BCryptPasswordEncoder를 Spring이 관리하게 함


[6] 자바 기초 - static / final
----------------------------------------

■ static
- "안 바뀐다"는 뜻이 아니라 "객체(인스턴스)가 아니라 클래스 자체에 속한다"는 뜻
- 일반 필드(인스턴스 필드): 객체마다 각자 따로 가짐
- static 필드: 클래스 전체가 딱 하나만 공유해서 씀
- static 필드도 값이 얼마든지 바뀔 수 있음 (예: 카운터)

■ final
- "한 번 값을 정하면 그 이후로는 절대 재할당할 수 없다"는 뜻 (진짜 "안 바뀐다"는 이 키워드가 담당)

■ static final = 상수(constant)
- 클래스 전체가 공유 + 절대 안 바뀜
- 관례상 이름을 대문자+언더스코어로 씀 (PAGE_SIZE, PAGE_BLOCK)
- private static final이면 같은 클래스 안에서만 재사용 가능 (다른 클래스에서 쓰려면
  public으로 바꾸거나, 별도 상수 클래스로 분리해야 함)


[7] Model
----------------------------------------

■ Model이 뭔가
- Spring이 자동으로 만들어서 넘겨주는, Controller와 View(Thymeleaf) 사이를 이어주는 데이터 저장소
- 쉽게 말하면 Map<String, Object>와 비슷한 역할
- 파라미터에 Model model 이라고 선언만 하면 Spring이 알아서 객체를 만들어서 줌

■ model.addAttribute("이름", 값)
- Map의 put("이름", 값)과 사실상 같음
- Controller에서 넣어준 이름(key)과, HTML에서 ${이름}으로 꺼내쓰는 이름이
  글자 하나하나(대소문자 포함) 정확히 일치해야 함

■ 서버사이드 렌더링(Thymeleaf)이라는 것
- Model에 담긴 데이터는 브라우저에 도착하기 전에 이미 서버에서 HTML 안에 다 박혀서 완성됨
- React 같은 별도 프론트엔드를 쓴다면, 그때는 @RestController가 JSON을 내려주고
  브라우저의 자바스크립트가 그 JSON을 받아 화면을 그리는 완전히 다른 방식이 됨


[8] Thymeleaf 문법
----------------------------------------

■ th:each - 반복문 (자바의 for(:) 와 동일)
  <tr th:each="board : ${boardList}"> ... </tr>

■ #numbers.sequence(시작, 끝) - 숫자 범위 리스트 생성
  <span th:each="i : ${#numbers.sequence(1, totalPage)}">
- 앞에 #이 붙은 것들(#numbers, #lists, #temporals)은 Thymeleaf가 기본 제공하는 유틸리티 객체
  → #을 빼먹으면 "그런 이름의 변수를 찾아라"가 되어버려서 에러남

■ th:if / th:unless - 조건부 렌더링
- th:if: 조건이 참일 때만 그 태그를 화면에 그림
- th:unless: th:if의 반대, 조건이 거짓일 때만 그림

■ th:classappend - 조건에 따라 CSS 클래스 추가
  th:classappend="${i == currentPage} ? 'active' : ''"

■ Fragment (조각 재사용)
- 여러 화면에서 반복되는 부분(헤더 등)을 한 파일에 정의해두고 다른 화면들이 가져다 씀
- th:fragment="이름": "이 부분은 재사용 가능한 조각이다" 선언
- th:replace="~{경로 :: 조각이름}": 그 조각을 가져와서 끼워넣기
  - th:replace: 부르는 태그 자체를 프래그먼트로 완전히 바꿔치기 (많이 씀)
  - th:insert: 부르는 태그는 남기고, 그 안에 프래그먼트를 끼워넣음
- 로그인 여부에 따라 다르게 보이는 것은 Fragment 자체의 기능이 아니라,
  Fragment 안에서 th:if/th:unless를 그냥 쓴 것뿐임
  (Fragment 재사용 + 조건부 렌더링, 두 기능의 조합)


[9] 페이징(Pagination)
----------------------------------------

■ LIMIT / OFFSET
- "전체 중 일부만" 가져오는 SQL 문법
- offset = (페이지번호 - 1) × 페이지당개수
- 예: 페이지당 10개, 2페이지 → offset=10 → "10개 건너뛰고 10개 가져와"

■ 전체 페이지 수 계산
- 목록 조회 쿼리와 별개로 "개수만 세는" 쿼리(COUNT(*))가 필요함
- totalPage = Math.ceil(전체개수 / 페이지당개수)  ← 올림 처리 (딱 안 나눠떨어져도 마지막 페이지 보장)

■ 페이지 "블록" (페이지 번호 10개씩 묶어서 보여주기)
  int startPage = ((currentPage - 1) / pageBlock) * pageBlock + 1;
  int endPage = Math.min(startPage + pageBlock - 1, totalPage);
- "<" 는 이전 블록으로 이동 (startPage - 1), ">" 는 다음 블록으로 이동 (endPage + 1)

■ MyBatis @Param
- 파라미터가 2개 이상일 때, MyBatis에게 "이 값은 이 이름이다"라고 알려주는 어노테이션
- 파라미터 1개일 땐 없어도 되지만, 2개 이상이면 필수


[10] DB / SQL - JOIN
----------------------------------------

■ JOIN이 필요했던 이유
- board 테이블엔 user_seq(작성자 번호)만 있고, 실제 이름은 user 테이블에 있음
- 화면에 "글쓴이" 이름을 보여주거나, 나중에 작성자로 검색하려면 두 테이블을 연결해서 조회해야 함

■ JOIN 문법
  SELECT ...
  FROM board b
  JOIN user u ON b.user_seq = u.user_seq
- "board의 user_seq랑 user의 user_seq가 같은 행끼리 짝지어서 합친다"는 뜻
- b, u는 테이블 별칭 (어느 테이블 컬럼인지 명확히 구분하기 위해 붙임)
- 이 패턴을 board 목록/상세 조회, comment 목록 조회에 전부 적용함


[11] 로그인 / 보안 (5단계에서 배운 것)
----------------------------------------

■ 비밀번호 해싱 (BCrypt)
- 평문 저장 금지 → BCryptPasswordEncoder로 암호화해서 저장
- encode(원문) → 해시값 저장, matches(입력값, 저장된해시)로 로그인 시 검증

■ 세션(HttpSession) 기반 로그인
- 로그인 성공 시 session.setAttribute("loginUser", user)로 세션에 저장
- 로그아웃은 session.invalidate()

■ 권한 체크 (본인 글만 수정/삭제)
- board.getUserSeq() == 로그인한 사용자의 userSeq 비교해서 다르면 차단
- 프레임워크(Spring Security) 없이 직접 세션 값 비교하는 수동 방식으로 구현
